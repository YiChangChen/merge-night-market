## 順利的地方

- **美術先行。** 提示詞、素材表、去背腳本在 S3.1 之前就完成，程式從第一個 story 就用正式圖。`sprite_tools.py` 抽成共用，E4、E5 可以直接沿用。
- **規則層先行，測試做到窮舉。** `resolveDrop` 的 6 種判定、各種邊界、10 道配方逐一觸發，都在規則層測完。UI story 只需要處理呈現。
- **沒動拖曳手勢也加上了新動畫。** 放開時查一次判定、用 `releasePlan` 決定動畫，e4be9f6 調好的手感完全沒碰到，diff 有確認。
- **三層審查這次都跑完了。** 「選取記的是格子編號」被三層同時抓到，這種跨 story 的問題，單一 story 的測試看不到。

## 卡關的地方

1. **story 的界線和實際依賴不一致。** S3.2 的 AC 要求 UI 不再呼叫 `movePiece`，可是一接上 `applyDrop`，玩家就能做出發明菜，而畫發明菜是 S3.3 的範圍。最後只好在 S3.2 先做一個「不會壞」的最小版本。
2. **用位置記住的 UI 狀態會跑掉。** 選取記的是格子編號，結果賣掉最後一份、升級用掉發明菜、產生器補進同一格時，選取都跳到別的棋子上。改成記棋子 id 才解決。
3. **測試通過的理由不對。** 防連點的測試一開始就算拿掉保護也會通過，因為規則層本身也會擋。要暫時拿掉保護、確認測試會失敗，才證明它真的有在測。
4. **模組互相依賴。** `sellPiece`（engine）要用 `dishSellPrice`（invention），可是 invention 已經依賴 engine，只好把價格函式搬回 engine。
5. **工具規則的小陷阱。** React Compiler 的 lint 不允許在 render 時呼叫 `Date.now()`；`board.tsx` 本來就不符合 Prettier，所以不能整檔重排。

## 關鍵心得

- 寫 story 時，如果規則和 UI 拆在不同的 story，要先確認規則 story 的 AC 會不會逼著 UI 一起改。
- UI 狀態要記「哪一個東西」（id），不要記「在哪裡」（位置）。
- 「防止某件事」的測試，要暫時拿掉保護、看它失敗一次。

## 重要發現（影響 Epic 4）

- **交單目前只認品項。** `findOrderCells` 只找 `kind === 'item'`。E4 的貴客單要交發明菜，S4.1 必須擴充交單規則（含扣 1 份、`count` 歸 0 清空），並同步更新訂單卡的「可以出餐」判斷。
- **阿嬤保底的資料已經準備好。** S3.2 的 `invent_rejected` 帶著受影響、尚未發現的配方。依使用者決定，相關配方都發現過時改走交換，不會送出這個事件。S4.4 的 `recordRejection` 直接接上即可。
- **線索單會改 `needsTick`**（S4.2），要套用 E2 的 A3：測正常、到期、時鐘倒退、快轉後歸零四種情境。
- **E4 美術**：`art-manifest` 第 42 列（阿嬤提示立繪）還是占位，E4 完成定義要求定稿。
